## 2.3 Runtime components and data flow

Flow when the user saves a rule set:

1. Options page validates with Zod, runs the compiler locally for badges, and
   writes `RuleSet` to `storage.local` (`ruleset.v1`).
2. Background listens on `storage.onChanged`, loads `Capabilities` for the
   running browser, runs `normalize` then `compile`.
3. Compiler returns `{ dnrRules, fallbackRules, report }`. `report` lists, per
   rule and per leaf, the engine that will evaluate it and any problem
   (`regexUnsupported`, `headerNotAllowlisted`, `overBudget`, `unsupportedHere`).
4. Background checks the budget (§2.6.5); on failure it writes the report and
   stops, leaving the previous rules active. On success it replaces dynamic
   rules atomically (`updateDynamicRules({removeRuleIds: previous, addRules})`).
5. Background configures the fallback engine. It registers the content
   scripts only if at least one fallback rule exists, and only for hosts the
   user has granted.
6. Report is stored under `compile.report.v1`; the UI shows badges from it.

The background is **stateless**: everything lives in `storage.local` or
`storage.session`, because both browsers terminate service workers.

## 2.4 Rule model (`packages/core/src/model`)

```ts
type RuleSet = { schemaVersion: 1; rules: Rule[]; settings: Settings };

type Rule = {
  id: string;              // uuid
  name: string;
  enabled: boolean;
  condition: ConditionNode;
  action: Action;
  resourceTypes?: ResourceType[];   // quick filter, ANDed with condition; default: all
  notes?: string;
  createdAt: string; updatedAt: string;
};
// Order in `rules` is the precedence (top wins). No separate priority field.

type ConditionNode =
  | { type: "group"; op: "and" | "or"; not?: boolean; children: ConditionNode[] }
  | { type: "cond"; not?: boolean; field: Field; operator: Operator; value: string | string[] };

type Field =
  | "url" | "scheme" | "host" | "port" | "path" | "query" | "queryParam"  // queryParam value: [name, expected]
  | "fragment" | "method" | "resourceType" | "initiatorDomain" | "domainType"
  | "requestHeader" | "requestBody" | "requestBodyField"                 // fallback only
  | "responseHeader" | "responseStatus";                                   // Chrome DNR / Tier A

type Operator = "equals" | "notEquals" | "contains" | "startsWith" | "endsWith"
  | "matchesRegex" | "matchesWildcard" | "in" | "exists" | "notExists"
  | "gt" | "lt";   // numeric: port, responseStatus

type Action =
  | { type: "redirect"; mode: "url"; url: string }                                   // http(s) only
  | { type: "redirect"; mode: "regexSubstitution"; pattern: string; substitution: string }
  | { type: "redirect"; mode: "transform"; transform: URLTransform }
  | { type: "block" }
  | { type: "allow" }
  | { type: "upgradeScheme" }
  | { type: "modifyHeaders"; request?: HeaderOp[]; response?: HeaderOp[] };          // HeaderOp: {name, op: set|append|remove, value?}
```

Rule file format: the same `RuleSet` JSON, exported as
`application/json` with `schemaVersion`. A single rule shares as
`rurl1:` + base64url(deflate(JSON)).

## 2.5 Precedence semantics (what the user sees)

The user orders rules top to bottom. The guaranteed semantics, identical on
both browsers:

1. For a request, the **topmost enabled rule whose condition matches and
   whose action is redirect, block, allow or upgradeScheme wins**. Lower rules
   of those types are ignored for that request.
2. **modifyHeaders rules are additive**: every matching modifyHeaders rule
   applies, topmost first, unless a matching `allow` rule sits above it.
   Header `set`/`remove` from a higher rule blocks later changes to the same
   header; `append` stacks (Chrome semantics; Safari applies first
   set/remove and ignores later ones, which is the same outcome).
3. A redirect never re-triggers the **same** rule on its own target (loop
   protection, §2.6.4). It can trigger other rules, as the user expects
   (chains).

Mapping to DNR: `priority = (N - index) * 8 + 4` gives each rule a band of
8 values. Within a band: anti-loop `allow` rules take `+1`. Chrome resolves
equal priorities by action type (allow > block > upgradeScheme > redirect)
and Safari sorts the same way, but we never rely on ties between user rules.
Across other installed extensions Chrome's cross-extension rules apply (block
wins, then redirect, then allow, newest extension first); out of our control
and stated in the docs.

## 2.6 Compiler: condition tree → DNR (`packages/core/src/compile`)

### 2.6.1 Normalisation

The tree is normalised to **disjunctive normal form (DNF)**: `NOT` is pushed
to the leaves (De Morgan), then the tree is expanded to `OR` of `AND`
groups. Each disjunct becomes one DNR rule with the rule's action and band
priority. This is what makes an arbitrary AND/OR designer fit DNR's single
flat condition per rule.

Limits: a hard cap of **64 disjuncts per rule** after expansion; the designer
warns at 16 and refuses above 64 ("simplify this rule or split it"). A
property test checks that the DNF and the original tree have the same truth
table on random inputs.

### 2.6.2 Leaf mapping per disjunct

| Leaf | DNR mapping (both targets unless noted) |
|------|------------------------------------------|
| `host equals/endsWith X` | `urlFilter` prefix `\|\|X^` (preferred over `requestDomains`, see Safari note) |
| `host notEquals X` | `excludedRequestDomains: [X]` |
| `method in [...]` | `requestMethods` (lower-case) |
| `method notIn [...]` | `excludedRequestMethods` |
| `resourceType in [...]` | `resourceTypes`; `notIn` → `excludedResourceTypes` (never both). **Always emit an explicit `resourceTypes` list** (default: every type the target supports), because omitting it excludes `main_frame` in both browsers |
| `initiatorDomain in / notIn` | `initiatorDomains` / `excludedInitiatorDomains` |
| `domainType` | `domainType` |
| `responseHeader`, `responseStatus` (Chrome) | `responseHeaders` / `excludedResponseHeaders`; on Safari → Tier A |
| exactly one URL-ish leaf with `contains/startsWith/endsWith/equals/matchesWildcard` | one `urlFilter` using `\|`, `\|\|`, `^`, `*` |
| several URL-ish leaves, or any `matchesRegex`, or `port`/`scheme`/`queryParam` exactness | one anchored `regexFilter` in the portable subset (§2.6.3), host folded in |
| `requestHeader*`, `requestBody*` | not compilable → disjunct goes to the fallback engine |
| `queryParam equals` | two disjuncts: `[?&]name=value&` and `[?&]name=value$` (no `\|` available), see §2.9 |

Safari-specific rewrites (target `safari`):

- Host is always folded into `urlFilter`/`regexFilter`; `requestDomains` is
  never emitted because WebKit ignores it when `regexFilter` is present and
  expands it per domain otherwise.
- A trailing `^` in `urlFilter` does **not** match end-of-URL in WebKit (it
  becomes `[^a-zA-Z0-9_.%-]` with no end alternative). When the pattern can
  end the URL, emit a second rule anchored with `\|`.
- `resourceTypes` drops `object`, `csp_report`, `webbundle`, `webtransport`.

### 2.6.3 Portable regex subset

Everything the compiler emits as `regexFilter` is in the intersection of RE2
(Chrome) and WebKit's `URLFilterParser`:

| Allowed | Not allowed (either engine, or Safari) |
|---------|-----------------------------------------|
| ASCII literals, metacharacters escaped with `\` | non-ASCII (hosts are punycode, the rest percent-encoded) |
| `.` | `\d \w \s \b` and inverted classes |
| bracket classes `[a-z0-9]`, negated `[^/?#]` | alternation `\|` |
| `?` `*` `+` (`{0,1}` `{0,}` `{1,}`) | counted `{n}` `{n,m}` |
| one leading `^`, one trailing `$` | `^`/`$` elsewhere |
| plain capture groups `( )` **[spike]** | look-around, backreferences, inline flags `(?i)` |

Chrome additionally limits a compiled regex to 2 KB and 1,000 regex rules
per ruleset type, so `urlFilter` is preferred whenever it is exact.
User-entered `matchesRegex` patterns are checked against this subset in the
designer; on Chrome, patterns outside the subset but valid RE2 are allowed
with a "Chrome only" badge; on Safari they are refused with the exact
construct named.

### 2.6.4 Loop protection

At compile time the evaluator runs the rule's own condition against a sample
of the redirect target (static `url`, or the transform applied to a
representative matching URL). If it matches, the compiler emits an `allow`
rule for the target at band priority `+1` and the report flags
`selfRedirectLoop`; the designer shows "this redirect would match itself,
an exception was added". Chains across different rules are allowed; Chrome
and Safari both stop runaway chains with their own redirect limits.

### 2.6.5 Budget

| Target | Budget constant | Counted as |
|--------|-----------------|------------|
| Chrome | 5,000 unsafe dynamic rules (redirect + modifyHeaders), 30,000 total, 1,000 regex | emitted DNR rules by type |
| Safari | 30,000 dynamic + session (shared), 150,000 content-blocker rules | **expanded** rules per DNR rule: `base × (1 + [initiatorDomains and excludedInitiatorDomains both set] + [action is upgradeScheme]) + excluded`, where `base = max(1, \|requestMethods\|)` (we never emit `requestDomains`) and `excluded = max(1, \|excludedRequestDomains\|) × max(1, \|excludedRequestMethods\|)` when either list is non-empty, else 0 |

`core/src/compile/budget.ts` computes both numbers; the apply step refuses to
exceed `min(constant, Capabilities.measured)` and reports the rule that
pushed it over. Nothing is ever silently truncated.

### 2.6.6 Output and ids

- Rule ids: deterministic `hash(ruleId, disjunctIndex) & 0x7fffffff`, so a
  re-compile replaces rather than duplicates. A collision check falls back to
  the next free id and stores the map.
- `isUrlFilterCaseSensitive: false` always (both default to false now, but
  Safari changed its default in 16.4).
- Every regex is validated with `isRegexSupported` before apply; on failure
  the report records `regexUnsupported` with the reason.
- The compiler is pure and covered by golden files per target
  (`fixtures/*.designer.json` → `*.chrome.dnr.json`, `*.safari.dnr.json`,
  `*.report.json`, `*.safari.expanded-count`).

## 2.7 Fallback engine (`packages/extension/lib/fallback`)

For conditions DNR cannot express. Each tier is labelled in the UI with its
exact limitation. The evaluator from `core` is the single source of truth for
matching; the tiers only differ in where they get the request data and how
they act.

### Tier A — observe navigations, then re-navigate (documents only)

- Listens non-blocking on `webRequest.onBeforeSendHeaders` (request
  headers), `onBeforeRequest` (`requestBody` for POST form/raw bodies) and,
  on Safari, `onHeadersReceived` (response headers/status, which Chrome
  handles in DNR). Listeners are synchronous (Safari requirement).
- Main-frame match → `tabs.update(tabId, {url})`; sub-frame match →
  `scripting.executeScript` in that frame → `location.replace(url)`;
  block → `tabs.update` to an extension-owned "blocked by rule X" page.
- Honest limits shown in the UI: the original request has already started
  (the server may see it once), only navigations can be acted on, and
  bodies are only visible for POST/PUT **[spike on Safari]**.

### Tier B — in-page shim (fetch, XHR, sendBeacon, form submit)

- `scripting.registerContentScripts` with two scripts for granted hosts:
  `bridge.ts` (isolated world, `document_start`) and `main-world.ts`
  (`world: "MAIN"`, `document_start`). Registered only while at least one
  fallback rule exists; unregistered otherwise, so the extension has no
  page-level footprint by default.
- `main-world.ts` wraps `window.fetch`, `XMLHttpRequest.prototype.open /
  setRequestHeader / send`, `navigator.sendBeacon`, and listens to `submit`
  events in the capture phase (gives body conditions for **form navigations
  before the request starts**, which Tier A cannot do).
- **Rule data never enters the MAIN world.** The shim sends
  `{method, url, headers, bodyPreview}` as a JSON string in a `CustomEvent`
  to the isolated world and reads the synchronous answer
  (`{action, url?, headers?}`) from a reply event dispatched inside the
  handler. Cross-world `CustomEvent` dispatch is synchronous in Chromium;
  Safari **[spike]**; if Safari is asynchronous, `fetch`/XHR stay fine (they
  are async anyway) and only `sendBeacon`/sync XHR degrade to "no action".
- Actions in page: rewrite URL before send (redirect), reject the promise /
  abort the XHR with a 0-byte response (block), add/remove headers
  (modifyHeaders, including **custom header names on Safari**, which DNR
  refuses there).
- Limits shown in the UI: only requests the page starts from JavaScript or
  forms; no `HttpOnly` cookies or forbidden headers; a page can detect or
  overwrite the shim (it is best effort, not a security boundary).
- The injection itself is performed by the browser through the `scripting`
  API, so the page's CSP cannot block it; the shim must never use `eval`,
  `new Function` or inserted `<script>` elements, which CSP would govern.
  The v1.0 note saying CSP may block injection is withdrawn.

### Tier selection

A fallback disjunct is evaluated by Tier B when the request is page-initiated
and by Tier A when it is a navigation. The report tells the user which tier
each fallback leaf uses, and the match log records `engine: "dnr" | "tierA"
| "tierB"` per hit.

## 2.8 Permissions, manifest, capabilities

```jsonc
{
  "manifest_version": 3,
  "permissions": [
    "declarativeNetRequest",
    "declarativeNetRequestWithHostAccess",   // redirect + modifyHeaders in both browsers
    "storage", "scripting", "tabs", "webRequest", "webNavigation", "activeTab"
  ],
  "optional_permissions": ["declarativeNetRequestFeedback"],   // match log; Chrome shows it only unpacked
  "optional_host_permissions": ["<all_urls>"],
  "background": { "service_worker": "background.js" },
  "action": { "default_popup": "popup.html" },
  "options_ui": { "page": "options.html", "open_in_tab": true },
  "browser_specific_settings": { "safari": { "strict_min_version": "26.0" } }
}
```

Host access is requested per rule: saving computes the origin patterns the
rule needs (source host, and the redirect destination host, which Safari
requires too) and calls `permissions.request`. `permissions.onAdded /
onRemoved` trigger a recompile, because Safari drops rules for hosts without
access.

`lib/capabilities.ts` returns a `Capabilities` object: static facts per
browser from `core/src/capabilities/{chrome,safari}.json` (produced by the
Phase 0 probe harness, `05-testing-ci.md` §5.2) plus runtime checks
(`isRegexSupported` probe, measured rule limit). The compiler and the
designer both consume it.

## 2.9 Worked example

Rule "Staging API switch" (user story U2 + U3):

```
Match ALL of
 ├─ host ends with "api.example.com"
 ├─ method is one of [POST, PUT]
 └─ Match ANY of
     ├─ query param "env" equals "staging"
     └─ request header "X-Env" equals "staging"
Action: redirect, transform host → "api-staging.example.com"
```

DNF: `D1 = host ∧ method ∧ queryParam`, `D2 = host ∧ method ∧ requestHeader`.
`D2` contains a request-header leaf → fallback (Tier A for navigations, Tier
B for page calls). `D1` compiles to DNR. Query-param exactness needs the
"value followed by `&` or end" split, so `D1` becomes two DNR rules.

Chrome output (rule at index 0 of 3 → band priority 28):

```json
[
  { "id": 1183720411, "priority": 28,
    "action": { "type": "redirect", "redirect": { "transform": { "host": "api-staging.example.com" } } },
    "condition": { "urlFilter": "||api.example.com^*^env=staging^", "requestMethods": ["post", "put"],
                   "resourceTypes": ["main_frame", "sub_frame", "stylesheet", "script", "image", "font",
                                     "object", "xmlhttprequest", "ping", "csp_report", "media", "websocket",
                                     "webtransport", "webbundle", "other"],
                   "isUrlFilterCaseSensitive": false } }
]
```

(Chrome's `^` also matches end-of-URL, so one rule suffices.)

Safari output: the trailing `^` does not match end-of-URL in WebKit, so the
compiler emits a second rule with `||api.example.com^*^env=staging|`, and the
`resourceTypes` list drops `object`, `csp_report`, `webtransport` and
`webbundle`. Expanded content-blocker count: 2 rules × 2 methods = **4**,
recorded in the report.

Fidelity report excerpt:

```json
{ "ruleId": "…", "engine": "mixed",
  "leaves": [
    { "path": "0", "engine": "dnr" }, { "path": "1", "engine": "dnr" },
    { "path": "2.0", "engine": "dnr" },
    { "path": "2.1", "engine": "fallback", "tiers": ["A", "B"], "reason": "requestHeader" } ],
  "dnrRuleCount": { "chrome": 1, "safari": 2, "safariExpanded": 4 },
  "warnings": [] }
```

## 2.10 Storage, data, migrations

- `storage.local`: `ruleset.v1`, `settings.v1`, `compile.report.v1`,
  `capabilities.measured.v1`.
- `storage.session`: `matchlog` ring buffer (last 200 hits: rule id, URL,
  engine, timestamp) for the popup.
- No `storage.sync` (Safari does not sync it), no remote code, no telemetry,
  no network calls by the extension itself.
- `core/src/migrate` holds `v0 → v1 …`; background runs them on
  `runtime.onInstalled` (`reason: "update"`). Exports carry `schemaVersion`.
